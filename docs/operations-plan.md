## 0. 現状（2026-11-13 実測）

- 掲載6件。スキーマv2（`data/places/*.yaml` が正本、Hugoテンプレートで描画）。
- 既に持っている鮮度関連の仕掛け:
  - `status: active` フィールド（全件）
  - `_verification.checked_at`（生成時の照合日）と `closed_check`
  - `related_posts.captured_at`（関連投稿の取得日）と `found_count`
  - `featured` フラグ（現状はカードのCSSクラスにのみ使用）
  - イベントの「（終了）」表示は `layouts/partials/place-card.html` が**ビルド時点の `now`** で判定（`timeZone = "Asia/Tokyo"` 設定済み）。
- デプロイは GitHub Actions（`pages.yml`）。トリガーは **push（main）と workflow_dispatch のみ**。
- このサイト用の cron はまだ無い。

**重要な含意**: 日付に依存する表示（終了判定、後述のイベントセクション）は「最後にビルドした日」基準になる。push が無い日が続くと表示が古びる。したがって「データ変更が無くても毎日再ビルドする」ことが鮮度の下支えになる（§2.3、§4）。

## 1. 鮮度維持フロー（定期再確認）

### 1.1 何が古くなるか

| 陳腐化の種類 | 具体例 | 主な検出方法 |
|---|---|---|
| 閉店・閉館・休館・移転 | 広島城の天守閉館（2026年3月）のように投稿から判明するケース | 関連投稿の再検索＋公式アカウント確認 |
| イベント期間の変更・翌年度日程 | ドリミネーションの年度更新（2026年度分へ差し替え済み） | 公式サイト／公式アカウント |
| 公式アカウントの変更・リンク切れ | アカウント名変更、サイトURL変更 | 公式プロフィール再確認 |
| 関連投稿の増加・内容の変化 | found_count 増加、「よく紹介されるもの」の顔ぶれ変化 | 横断検索の再実行 |
| 出典投稿の削除・埋め込み不可化 | 投稿削除、埋め込み無効化 | 出典URLの生存確認 |

### 1.2 再確認の3層構造

- **L1 日次（機械的・軽い）**
  - 全件の再ビルド（workflow_dispatch）。日付表示を当日に追いつかせる。
  - 出典投稿URLと公式リンクの生存確認（リンク切れはレポートのみ、自動修正しない）。
- **L2 週次ローテーション（再調査）**
  - `_verification.checked_at` が古い順に週N件（開始時は3件、§5参照）を再調査する。
  - 内容: 関連投稿の再検索（`found_count`・`captured_at` 更新、上位itemsの入替）、公式アカウントの現行確認、閉店・休館・移転キーワードの検出、`highlights` の見直し。
  - 変化が無くても `checked_at` は更新する（「確認した」こと自体が鮮度の証跡になる）。
- **L3 イベント・季節連動（重点）**
  - イベント: 開始30日前と7日前に期間・内容を公式で再確認。終了翌日に終了状態と翌年度情報の有無を確認。
  - 季節タグ（桜・紅葉・イルミネーション・夏のイベント等）を持つスポットは、季節入り前に一括再確認。

### 1.3 反映ルール（自動反映と承認待ちの線引き）

鮮度と「GitHub書込みは原則承認制」の両立のため、反映を2段に分ける。

- **D1決定（2026-11-13）: 反映範囲に制限を設けず、すべて自動更新してよい。** `found_count` 等の数値・日付、`related_posts.items`、`highlights`、`status` の変更、`summary` の書き換え、`period` の変更まで自動反映する。
- ただし `status` の変更（閉店・休館）と掲載の取り下げは、実施後に必ず週次レポートで事後報告する。
- 疑いの扱いは D5: エビデンス（公式発表、または独立した複数投稿での言及）があれば、疑いの段階でも `notices` として掲示する。エビデンスが無い場合は内部状態 `status: needs_review` にとどめ、次回確認で優先的に裏取りする。

### 1.4 誤情報検出（別仕組み）との接続

- 検出側が書き戻してよいのは `status` フィールドのみ（契約は data-format-decision.md の方針通り）。
- 検出側が `needs_review` を立てた件は、週次ローテーションの先頭に割り込ませて優先確認する。

## 2. ホーム画面のイベント表示

### 2.1 セクション設計「開催中・まもなく開催」

- 配置: トップの絞り込みナビの上（または直下）。通常の一覧とは別枠で見せる。
- 対象: `kind: event` かつ `period.end >= 今日` かつ `period.start <= 今日＋表示窓`（表示窓は D2、案は45日）。
- 並び順: 開催中を先に（終了日が近い順）、続いて未開始（開始日が近い順）。
- カードの追加表示: 「開催中」バッジ／開始前は「あとN日」／終了7日前からは「まもなく終了」。
- 該当0件のときはセクション自体を出さない。

### 2.2 実装方式

- **方式A（推奨）: ビルド時判定** ― 既存の終了判定と同じ仕組み（Hugo の `now`）。単純で表示が安定する。鮮度は再ビルド頻度に依存するため §2.3 とセット。
- 方式B: クライアントJS判定 ― 訪問日基準で常に正しいが、初期描画のちらつきと、本文HTMLに残らない弱さがある。将来、件数が増えて再ビルド間隔が問題になったら併用を検討。

### 2.3 再ビルドの保証

- 毎朝、データ変更が無くても `pages.yml` を workflow_dispatch で回す日次cronを置く（冪等。当日の1件追加pushがある日は結果的に二重になるが害はない）。
- これにより終了判定・イベントセクション・「あとN日」が最大でも1日遅れに収まる。

## 3. リコメンド

### 3.1 Phase 1 ― テンプレートのみ（データ追加なしで実装可能）

- **詳細ページの関連表示**: 「同じエリアのおでかけ先」（`area.label` の市区一致）と「同じジャンルのおすすめ」（`kind` 一致＋`tags` 共通数順）を各最大3件、詳細ページ下部に自動表示。
- **Newバッジ**: `added_at` から14日以内はカードに「New」を付け、一覧の先頭側で目立たせる。

### 3.2 Phase 2 ― 編集枠（おすすめ欄）

- **「今月のおすすめ」**: 既存の `featured` フラグを活用し、トップ上部に最大3件を別枠表示。選定方式は D4（手動／季節タグ自動／併用）。
- **季節のおすすめ**: `tags` の季節語（桜・紅葉・イルミネーション・海・夏祭り等）と現在月から自動編成するセクション。featured とは別枠にできる。

### 3.3 Phase 3 ― データ連動（将来）

- GA4 をこのサイト専用に用意し（amazon-hikaku.com とは別プロパティ）、詳細ページ閲覧数と関連リンクのクリックで編成を調整。
- 関連投稿のいいね数推移を並び替え材料にする。

## 4. 運用カレンダー（cron設計案）

| 頻度 | ジョブ案 | 内容 |
|---|---|---|
| 日次・朝 | 再ビルドdispatch | データ変更なしでも `pages.yml` を回し、日付表示を当日に保つ |
| 日次・夜 | 5件追加（2026-11-13決定、cron: odekake-add-daily） | 候補プール優先＋不足分は新規探索→検証ゲート→YAML追加→push。ゲート通過で自動掲載し、結果を事後報告 |
| 週次（月曜） | 再確認バッチ | L2ローテーション（総件数の1/8・最低3件）＋L3の該当分。変更は自動反映し、status変更・取り下げは事後報告 |
| 月次（1日案） | 月次サマリー | status別件数、最も古い `checked_at`、来月のイベント一覧、featured差し替え候補の提示 |

- 時刻はいずれも他ジョブと衝突しない「:37」系に寄せる。
- 週次・月次は「変化が無ければ無報告」ではなく、確認件数だけでも一報する（止まっていないことの可視化）。

## 5. スケーラビリティ試算

- 再確認1件の作業量は新規追加の半分程度（再検索＋公式確認が中心）。
- 週3件ローテーションの場合: 6件→2週間で全件回転／30件→10週間／50件→約4ヶ月。
- kind別の推奨周期（閉店リスクの高い順）: shop＝月1回、stay・activity＝2ヶ月に1回、spot＝3ヶ月に1回、event＝期間連動（§1.2 L3）。
- 件数が50件を超えたら、週の再確認件数を増やすか、周期の長いkindを隔週に落とす調整が要る。

## 6. 鮮度の「見せ方」

- 詳細ページに **「情報を確認した日」（`_verification.checked_at`）を表示**する。前回議論した差別化ポイント（根拠と確認日が見える）と直結する施策（D6）。
- 閉店・休館が**確定**したら `status` を変更し、一覧では薄く表示＋詳細に明記。**疑い**の段階では断定せず、必要な場合のみ「休館等の情報があります。公式サイトでご確認ください」＋公式リンクへの誘導にとどめる（D5）。
- 前回からの宿題（広島城の天守閉館・こども文化科学館の休館予定を書くか）への答えとして、この「確認日つきの注記」という形式を推す。推しポイントである正直さ・鮮度と一致し、断定リスクも避けられる。

## 7. 判断事項（2026-11-13 すべて確定）

- **D1**: push に制限は設けない。**全部自動で更新してよい**（status変更・取り下げは事後報告）。
- **D2**: ホームのイベント表示窓は **60日**（方式A＋日次再ビルドdispatch）。
- **D3**: 週次再確認は **月曜**。件数は当初3件で開始し、同日中に「総件数の1/8（切り上げ）・最低3件」の件数連動へ変更した。
- **D4**: 「今月のおすすめ」は **全自動**（ルールで選定: §3.2 の編集枠を月次ジョブが自動編成）。
- **D5**: 閉店・休館の疑いは、**エビデンスがあれば掲示する**（エビデンス＝公式発表、または独立した複数投稿での言及）。
- **D6**: **ページの更新日付を記載する。更新の区間（セクション）が異なる場合は、区間ごとに更新日時を記載する**（基本情報＝確認日、関連投稿＝取得日、出典と確認方法に両方を明記）。

## 8. 実装フェーズ

- **Phase 0（基盤）**: 日次再ビルドdispatchのcron化、詳細ページへの確認日表示（D6確定後）
- **Phase 1（見せ方）**: ホームのイベントセクション、詳細ページの関連リコメンド、Newバッジ
- **Phase 2（鮮度運用）**: 週次再確認cron（§1.3の反映ルールと承認フロー付き）
- **Phase 3（月次運用）**: 月次サマリー、featured運用開始、GA4検討

## 9. トップページ表示のスケーリング（2026-11-13 追記）

現状は全件をカードで表示している。実測ではカード1件あたり約1.6KB（テキストのみで画像は無い）。

- **〜100件**: 現状の全件表示で実用範囲（HTMLは約160KB程度）。
- **100件超えが見えたら**: ホームは「特集（イベント＋おすすめ）＋新着30件」に絞り、全件一覧は `/index.json` をJSで描画する一覧表示に分離する（30件ずつの「もっと見る」＋ジャンル／県の絞り込み＋キーワード検索）。詳細ページと sitemap は変わらないため、検索エンジンへの影響は小さい。
- **300件〜**: 県別・ジャンル別のアーカイブページ（content adapterで生成）を追加し、一覧の入口を分散する。
- 検知: 月次サマリーで総件数が80件に達したら、上記移行の検討時期として報告する。

## 10. UI/UX改善サイクル（2026-11-13 追記）

- 月次（15日）にUI/UXのレビューと小改善を行う（cron: odekake-ux-monthly）。
- レビュー観点: 表示崩れ（トップ＋詳細数件、ライト／ダーク両テーマ、モバイル幅）、テーマ切替の動作、Instagram埋め込みの表示、ページ重量、基本的なアクセシビリティ（フォーカス、コントラスト、タップしやすさ）。
- 1回あたりの自動適用は小改善1〜3件まで。対象は `layouts/` と `static/` の範囲で完結するものに限り、データ（YAML）とスキーマには触れない。結果は事後報告する。
- 大きなデザイン変更や情報設計の変更は自動適用せず、レポートで提案してユーザーの判断を待つ。
- 変えるべきものが無ければ無理に変えず、チェック結果だけを報告する。
- §9の表示スケーリング移行（80件トリガー到達時）も、このサイクルの実装候補として扱う。

## 11. 情報源アカウントの運用（2026-11-14 追記）

- 追加： 日次追加ジョブが、場所の調査（出典投稿・関連投稿の収集）の副産物として行う。調査中に出会った地域情報専門アカウントのうち、検証ゲート（プロフィール取得で実在確認／公開アカウント／直近30日以内に投稿あり／対象地域の情報発信が主軸／既存と重複なし）を満たすものを、1日最大2件まで追加する。アカウント探しの専用探索はしない。
- 機会更新： 既掲載のアカウントに日次調査で触れたら、手元にある範囲でフォロワー数・投稿数のスナップショットを更新し、人気の投稿もより反応の大きいものが見つかれば入れ替える。
- 一括更新： 月次ジョブが全アカウントのスナップショットと人気の投稿を再取得し、日次の機会更新で触れられなかった分の受け皿とする。取得できない場合は据え置きにして報告する。
- 追加したアカウントは日次報告で事後報告する（D1の全自動方針の範囲内）。
